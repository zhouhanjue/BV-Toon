### 1. ~~哈希防盗~~ → 1.6.0/1.7.0 这次交付已完成 ✓（实现要点留档）
* 打包时生成 `BVToonData/integrity.json`：**6 个顶层 `.py` + `BVToonShading.blend`** 的 SHA-256
  （生成端与校验端共用插件里的 `bv_integrity.py`，规则只有一份）
* 加载时（`register()`）+ 每次渲染前（`render_pre` 的 `force_watermark`）各核对一次，
  摘要按 (大小, mtime) 缓存，所以每次渲染只多几次 `stat`
* 处理器带 **`@bpy.app.handlers.persistent`**，并由 `mount_watermark_handler()` 在
  `register()`（每次启用）与面板绘制时各补挂一次 —— 这两条缺一个，"新建文件"或"重新启用插件"
  之后强制署名就会静默失效（见第三节第 13 条）
* **三态**（不是两态）：`ok` → 正常署名；`modified`（文件被改/丢失/多出一个 `.py`）
  → `未授权修改版 / UNAUTHORIZED MODIFIED COPY`；`unverified`（没有清单/清单读不懂）
  → `未验证副本 / UNVERIFIED COPY`。两种异常都是**红字、字号 24、不透明 + 半透明黑底**，
  且**不再读面板里那行自定义署名**（否则改个文字就洗白）
* 异常时：控制台打一整块警告 + 面板最上面一块红框告警（`alert=True`）；**从不阻止渲染**
* 诚实前提：哈希校验**不是加密**，懂行的能连清单一起改；它挡的是"随手改名就发"的人，
  并让改过的副本自己带着标记。GPL §7 附加条款第 2 条本来就要求"修改版必须标明与原始版本不同"，
  这个水印就是那条要求的技术实现 —— **不是新增限制**
* 自己改了代码要恢复正常水印：重跑 `tools\install_bv_toon.py`（或重新打包）重算清单即可

### 1c. 腮红只加在脸上 + 一定看得见（1.7.0 做、**1.7.1 重做**）✓
* 「添加腮红」以前**无差别写到每个卡渲材质上**（实测这个模型 39 个全中，衣服头发裙子腿一起红）
  ⇒ 现在先认脸（材质名 → 网格名 → 底色贴图名 → 头部几何 → 唯一肤色材质），只写它，
  **其余材质清零**；一种都没命中就**报警 + 列材质名**，绝不猜、绝不"干脆全加"
* 认出的结果写在 `bv_face_materials`（面板显示 `脸材质：颜`），依据写在 `bv_face_note`；
  猜的脸材质**面数 < 128** 时（那就是眼睛/嘴之类的零件，实测 鏡音リン 只有 58 面）
  面板会弹红字 + 报告里带 ⚠，让人选中真脸材质点「脸=当前材质」
* 模式＝`替换单个【材质】`时用当前激活的材质槽（不看名字）—— 给认不出脸的模型留的手动口子
* ⚠️ **遮罩绝对不能再"按亮度卡阈值"**（1.7.0 两次都栽在这，第 20 条有全过程）：
  现在是 **`遮罩 = 腮红保底 + (1 - 腮红保底) × 脸颊圈`**，纯几何，没有任何能整体归零的项
* **脸颊圈**怎么定（`bv_materials.blush_region`）：取脸材质自己的顶点 → 只留颈部以上 →
  在"脸的左右/上下"平面里挑**离目标点最近的真实顶点**当球心（保证球切得到颊面）→

* 组输入：**新增** `腮红保底 / 腮红左 / 腮红右 / 腮红半径 / 腮红软边`，

### 1d. 泛光按模型实测（1.7.2 的重点）✓
* 作者反馈："泛光不统一，胡桃等角色明显低于奥黛塔"。量下来属实：同机位、同参数，
  **奥黛塔剪影外那圈光 +0.160，胡桃只有 +0.017**（角色上的增量 +0.0497 vs +0.0060）
* 原因：泛光源是渲染的 Emit 通道 + 画面超 `阈值 0.95` 的部分，外发光还有"自发光 > 0.60"的门槛
  —— **整条链吃绝对亮度**，深色角色天然吃得少
* 试过但**否掉**：按"材质平均底色 × 亮度"折增益。材质均值预测不了"屏幕上亮部占比"：
  胡桃按材质算只要 1.44 倍，**实测要 ~9 倍**才追平 ⇒ 改成**直接测**
* 现在：点「添加泛光」渲两张 **192×192**（强度 0 / 当前），量"剪影外那圈光"（关着是黑、
  开着才亮、贴着剪影 2 px 以内），**闭环**最多迭代 `GLOW_ITERATIONS=3` 轮逼近目标
  `GLOW_HALO_TARGET=0.16`（奥黛塔在认可设置下量到的值）；**只往上调，不把亮的压暗**
* 实测结果：剪影外 **奥黛塔 0.152 / 胡桃 0.144 / 芙宁娜 0.142**（相差 1.07 倍，原来 7 倍），
  初音ミク按"只往上调"保持 0.271；胡桃角色上 +0.0060 → **+0.083**
* 量不出来（没相机 / 没框住 / 剪影外 < 12 像素）**如实说**（报告 + 场景属性 `bv_glow_note`），
  强度保持默认 0.10；测量期间临时摘掉强制署名处理器（白字会污染），**量完必须挂回去**——
  `audit_bv_toon.py` 现在专门断言这一条
* 验收：`tools\check_glow_uniform.py`（每个模型 ≥ 0.10 看得见、≤ 0.45 没糊、归一化过的
  模型之间 ≤ 1.6 倍）当前 `failures=0`；效果图 `_glow_demo\`；探针 `_scratch\probe_glow_models.py`

## 三、这个项目踩过的坑（同一类问题反复出现，务必先看）

**共同主题：名字/接口对不上就"静默失败" ✗**

0. **文档里的命令会撒谎（本次新踩）** —— HANDOFF 写的 `tools\package_bv_toon.py --source clean-room\BV-Toon`
   实测直接退出：那个名字下躺的是 MBTs 时代的旧脚本（指向工作区根目录的私有版，要 `BV_Toon_Fix.py`）。
   ⇒ **纪律：验证命令每写一次就要真跑一遍**；工具改名时**把旧名字让出来**，不要新旧同名共存
1. **静默 `try/except`** 是最大温床 —— Glare 参数一个没设上（画面绿色重影）、`install()` 提前返回导致操作符没注册、腮红操作不存在的节点（返回 FINISHED 却毫无变化）
   ⇒ **纪律：参数设置失败必须 `print`**（本项目靠这条捡回好几次）
2. **Blender API 差异**
   * `CompositorNodeGlare` 在 4.5/5.x 把选项搬到**插座**上，枚举**首字母大写**（`Bloom` 不是 `BLOOM`）；没有了 `glare_type`/`quality`/`mix` 属性
   * 组接口**不支持图片插座**（`NodeSocketImage` 报 enum 错）→ 图片要在材质树里采样、把结果用 Float 送进组
   * Frame 节点类型名是 **`NodeFrame`**，不是 `ShaderNodeFrame`
   * `bpy.app.handlers` 的列表**不支持切片赋值**；且工厂重置/重载会清空它 → 按名字去重后 append，并在**面板绘制时补挂**
   * `RenderSettings` 没有 `use_stamp_metadata`（烧录靠 `use_stamp_note`）
   * 引擎枚举：4.5 是 `BLENDER_EEVEE_NEXT`，5.2 是 `BLENDER_EEVEE`
   * Blender 的 stamp 是**一整块**：`use_stamp` 开了，`file/date/render time/timecode/scene/frame/camera/labels` 各自还开着 → 必须逐个关
3. **RNA 对象比较**：`node.parent is frame` **恒为假**（包装对象每次访问都重建）⇒ 必须用 `==`
4. **白名单清理**：只留 `bv_*` 前缀的节点 ✗ ⇒ **自己建的每个节点都要起 `bv_` 名字**，否则会被自己的清理吃掉（渐变查表链、腮红都栽过）
5. **mmd_tools 无法"重建"**：`convert_materials` 是**迁移**（源码里直接 `nodes.get("mmd_shader")`）⇒ 删掉原始节点就再也回不来
6. **显示名 ≠ 真名**：`MMDShaderDev`/`MMDTeXUV` 只是标签，真名是小写 `mmd_shader`/`mmd_tex_uv`
7. **PowerShell 陷阱**（工具脚本本身出错的常因）
   * 单引号字符串里 `` `r`n `` 是**字面量** ✗；双引号里才解释
   * 代码里带 `"` 的字符串别用双引号包 → 用 `@'...'@` here-string
   * `[IO.File]::ReadAllText` 的相对路径认**进程 CWD**，不是 PowerShell 的 `cd` ⇒ **一律用绝对路径**
   * `git commit -m` 的消息里别放 `"` ✗（会被拆成 pathspec）
   * 管道里的中文日志在控制台会显示成乱码（代码页），**别据此判断脚本报错** —— 看日志文件或退出码
8. **改文件的安全姿势**：精确锚点 → 替换后先 `ast.parse` → 再落盘；**多行/行尾混合时**改用"按行号或字符串下标"的 Python 手术（本次修坏过一次文件，靠这个方法救回）
9. **验收工具本身要可信**：曾经因为**背景不是黑的**，把分界链误判成"断了" ✗ ⇒ 渲图统计要 `film_transparent=True` + **只统计模型像素**（`alpha>0.5`）。
   本次做水印验证时反过来利用这点：**空场景 + `film_transparent`**，图上除了烧进去的水印不该有别的，
   于是"有没有水印/什么颜色"可以直接数像素（`_scratch\verify_watermark_pixels.py`）
10. **版本号会四处漂移**（本次收口）：条款弹窗里硬编码的 `BV-Toon 1.5.0` 不会跟着 `bl_info` 走
    ⇒ 现在版本**只在 `bl_info` 写一次**（`_VERSION`），面板底栏与条款标题都取它；打包脚本会**拒绝**硬编码版本号
11. **"装上去的字节"才算数**：安装脚本必须在目标目录**重算** `integrity.json`，
    否则装完的副本会被自己的校验判成「未验证副本」（清单描述的是打包那一刻的字节，而安装可能只同步一部分）
13. **`bpy.app.handlers` 比想象中脆（本次渲图当场抓到）** —— "强制署名谁也绕不过"其实是假的：
    * `wm.read_homefile`（文件 > 新建）与 `wm.read_factory_settings` 会**清空处理器列表**
      ⇒ 处理器必须带 **`@bpy.app.handlers.persistent`**（实测：不带标记的会被清掉，带的能活下来）
    * 工厂重置还会**把插件一起关掉**，而 Blender **重新启用**插件时**不会重跑模块顶层代码**
      （模块已在 `sys.modules` 里）⇒ 只写"文件末尾 append 一次"是不够的，必须在 `register()` 里补挂
    * "面板绘制时补挂"救不了后台渲染：没人画面板
    * **纪律：凡是靠 handler 生效的功能，都要有一条"重新加载之后还生效"的回归测试**（现在
      `package_bv_toon.py --verify` 与 `audit_bv_toon.py` 都会真渲一张 64×64：先把水印破坏成
      「入侵者」，再看处理器有没有把它设回来）
    * 同类问题也提醒过自己：`unregister()` 要顺手把处理器摘掉，不然插件关了它还挂着（已加）
14. **行尾（LF/CRLF）会悄悄改字节**（本次踩到）：本机 git 是 **`core.autocrlf=true`（system 级）**，
    checkout 会把仓库里的 LF 换成工作区的 CRLF ⇒ 同一份代码"刚 checkout 的工作区"和"打包时的字节"可以不同。
    清单只描述**它所在的那一份副本**，所以不会误报；但**换了来源就要重算清单**，而且 `dist\` 里那个 zip 的
    sha256 会跟着行尾变（想复现同一个 sha，先确认行尾）。
    另一个同类坑：Python 文本模式 `open(path, "w")` 在 Windows 上会把 `\n` 写成 `\r\n` ——
    本次就因此把一份安装副本写成了 CRLF（被 `_scratch\cmp_all.py` 抓出来，重装即愈）。
    **改文件要动字节时用 `newline=""` 或二进制模式**
15. **"验收工具自己假通过"比功能坏掉更危险**（本次做损毁功能时踩到）：像素检查当时报
    "21.7% 的像素变了 → 通过"，其实画面是**空的**（接线抛异常 → 合成器输入悬空 → 黑屏），
    跟"损毁生效"长得一模一样。⇒ 一条像素断言不够，必须同时钉住**结构**：
    * 合成器的输出插槽到底吃谁的输出（`sink_fed_by()` 必须是损毁节点）
    * 损毁节点自己的输入还连着（上游没丢）
    * **正常态的画面本身有内容**（`bright_fraction()` > 5%）—— 测试场景先得自己站得住
    * 损毁态也**不是黑屏**（> 2%），这样"弄坏"和"弄空"分得开
    还有个笨坑：我搭的棋盘测试平面一开始放在 XY 面上，相机是"侧着看"它 ⇒ 整幅图接近全黑。
    **搭测试场景也要先证明它拍到了东西**
18. **参数的"合理值"要量，不能拍；而且要按那个参数真正作用的部位去量**（做"腮红只给脸"时踩到）：
    腮红遮罩 = `clamp((范围 - 亮度) / 过渡) × 浓淡`，默认范围 **0.62**、看着挺保守 ——
    可是这张脸渲出来亮度中位数 **0.85**（脸上多在 0.9~0.97）⇒ **阈值对脸完全够不着**。
    只给脸加时实测 **0 个像素变化**；而"全都加"会变 6~11 万像素 —— 也就是说
    以前那个"腮红有效果"的观感，**全部来自衣服和皮肤**，脸上一分都没有。
    ⇒ 纪律：改一个阈值参数前，先量**目标部位**的实测分布（`_scratch\probe_face_luma.py`
    读渲好的图算分位数），再在真实模型上扫一遍取值（`_scratch\probe_blush_range.py`）。
    连带教训：验收断言也要挑**能看出强弱**的量 —— 第一版检查用"像素差 > 0.05"，
    浓淡 0.6 时它判"没变化"（其实是太淡），浓淡 0.8 才既看得见又过阈值
19. **别拿"别人的观感"当自己的实现依据 —— 但也别拒绝"只看行为"的对照**（做腮红这一轮）：
    * 用户提出"逆向 MBTs-NG 再仿制" ⇒ **先查事实再动手**：`MBTs-NG\` 目录其实是空的（0 文件，
      被 gitignore 的临时检出）；磁盘上只有私有改名版 `BV-Toon\`（**许可声明已被早先的去品牌
      工具洗掉，无从查证**）与 `dist\_old\` 的老 zip。而 clean-room 版自己的 README/LICENSE 写着
      "代码、节点图、资产全部自写，不含任何第三方插件的代码或资源"——照搬进来这几句就成了假的，
      §7 也没法对别人的代码主张署名。⇒ 走**行为级对照**（只跑它、不读代码），实现按第一原理重做
    * 对照方法也值得抄：`_scratch\probe_blush_behavior.py` 用**同一把尺子**（同机位、同模型、
      同像素阈值）量"点腮红前后"的变化像素/行范围/通道均值，两个插件各跑一次即可比
    * 结论：它的腮红也是只动脸部、只压 G/B（加红），比我们当时的纯着色器版更窄更浓
      ⇒ 于是我们改用**模型自带 `照れ` 贴图当遮罩**，比"仿一个阈值"强
    * 又一次"假设害死人"：以为 `照れ.png` 的图案能用亮度取 —— 实测 **98% 全透明、RGB 均匀浅粉**
      （亮度均值 0.858）⇒ 亮度当遮罩完全没用，必须用 **alpha**；而且 alpha 整体很淡
      （均值 0.02），直接乘只剩 38 像素 ⇒ 中间要加 `Map Range` 规整
    * 自己写出来的 bug 也记一下：接线时把"组输入插槽"变量名覆盖掉了，遮罩接到了 `Map Range`
      自己的插槽上（组的输入根本没接）—— 被 `check_blush_face.py` 的断言当场抓住。
      **变量名别复用**，尤其是"当前正在操作的那个插槽"
16. **打包必须可复现，否则文档里的 sha256 就是假的**（本次踩到）：清单那条 zip 记录原先用
    `time.localtime()`（"现在"）当时间戳 ⇒ **同样的源码每打一次 sha 都不同**，HANDOFF 里记的
    sha256 直接失效。改成取"源码里最新的那个 mtime"，并在 `main()` 里**自检**：
    用临时目录再打一次，两次 sha 不一致就 `REFUSING` 退出（现在会打印"可复现: 两次打包 sha 一致 ok"）
17. **Windows 控制台是 GBK，`print` 不认识的字符会直接崩脚本**（本次踩到）：
    `print("... ✓")` 抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2713'` ——
    复现性自检明明过了，却倒在"打印结果"那一行，`exit=1` 看起来像功能坏了。
    ⇒ 工具脚本开头统一 `sys.stdout.reconfigure(errors="replace")`（宁可打成 `?` 也别崩），
    装饰性符号（✓ ⚠ ✗）一律别用在 `print` 里
20. **"按亮度卡阈值"的遮罩必然会静默归零 —— 两次都栽在同一件事上（腮红 1.7.1 重做）**：
    * 第一次：绝对亮度阈值 `clamp((1.10 - 亮度)/0.30)`。老 PMD 模型的脸是**纯白贴图 × 亮度 1.05**，
      渲出来就 >1 ⇒ 这一项恒 0 ⇒ 初音ミク/MEIKO/鏡音リン **0 像素变化**
    * 第二次：以为"除以自己的峰值"就没事（`亮度/峰值`）⇒ 依然恒 0。探针
      `_scratch\probe_relative.py` 把组内部三个值当颜色通道渲出来量：**最终色是参考峰值的
      1.0~4.6 倍**，阈值照样够不着
    * **把它揪出来的那个实验**（值得抄）：`_scratch\probe_giant_cheek.py` 把脸颊半径设成 100
      （遮罩恒 1）—— 胡桃立刻有 **2300 像素**变化，默认半径只有 **21 像素** ⇒ 问题锁定在遮罩，
      不在"腮红有没有接进最终颜色"（那一步是好的）。**先隔离"有没有生效"和"值算得对不对"**
    * 结论：会归零的项就不能放在"看得见"的必经路径上。现在的遮罩 = `保底 + (1-保底) × 脸颊圈`
    * 附带两条：① "看得见"的门槛别只看"有没有像素变化"，要量**幅度**（腮红色跟肤色只差 0.2 时，
      最大像素差只有 0.05 —— 数字上"有变化"，人眼一片没有）；② 球心必须落在**曲面上的真实顶点**
      （原先按"中心 + 55% 凸出"算，球心落在头颅里面，球面只是擦过颊面）
21. **Blender 渲图不认相对路径 —— 而且是"静默不写"**（这轮因此浪费了一整轮测量）：
    `scene.render.filepath = "_blush_corpus\x.png"` + `write_still=True` **一个文件都不写、也不报错**；
    更坏的是紧接着 `bpy.data.images.load("_blush_corpus\x.png")` 竟然**不抛异常**，
    返回一张莫名其妙的图（同尺寸但内容不是它）⇒ 后面所有像素统计全是垃圾。
    ⇒ 所有验收/探针脚本一律 `os.path.abspath()` 处理输出目录（`check_blush_corpus.py`、
    `check_blush_face.py`、`probe_*.py` 都改过了）。**写盘的东西：先绝对路径，再谈数据**
22. **"猜"出来的东西要能被一眼看穿**（认脸这件事）：PMD 模型材质名全是 `材質N`、贴图共享 toon，
    只能按"头部区域里面积最大"猜（`_scratch\probe_face_pick.py` 把每个材质的点数/包围盒/头上面积/
    朝前面积列出来）。实测 鏡音リン 的候选只有 **58 面**（那是眼睛或嘴）—— 这时候硬猜等于白加，
    所以现在：**面数 < 128 就在面板弹红字 + 报告里带 ⚠**，并指着「脸=当前材质」让人自己指。
    宁可说"我认不出来"，也别默默加错地方
23. **"看起来一样"的量，要在屏幕上量，不要在数据上算**（泛光跨模型统一，1.7.2）：
    * 泛光吃绝对亮度 ⇒ 深色角色天然吃得少（奥黛塔剪影外 +0.160、胡桃 +0.017，差 7 倍）
    * 第一版想按"材质平均底色 × 亮度"折个增益 —— **错了**：材质均值预测不了**屏幕上亮部占多大比例**
      （胡桃按材质算 1.44 倍，实测要 ~9 倍）。**"数据里的平均值"和"画面上看得见的东西"是两回事**
    * 第二版直接渲两张小图量"剪影外那圈光"，但**一次测量仍不准**：泛光会把亮部顶到 1.0，
      响应不是线性的（奥黛塔每单位响应 0.10 时 1.49、1.2 时只剩 0.43）⇒ 改成**闭环迭代**
    * 还有个尺寸陷阱：量的那一圈要按**画面比例**取，不能取绝对值 —— 泛光半径本来就是画面百分比，
      96 px 取 3 px（3%）会把紧贴剪影的亮芯算进来，胡桃被量成 0.265、全分辨率其实只有 0.166
    * 顺带：**只往上调**。甲方要的是"别让深色角色比别人暗"，不是"把亮的也压下去" ——
      归一化很容易顺手把本来正常的角色改坏（这里 初音ミク 0.271 就保持原样）
    * 测量会临时动渲染设置（分辨率/署名/摘掉强制署名处理器）：**全都要还原**，
      而且要有断言盯着"处理器挂回去了没有"（`audit_bv_toon.py`、`check_glow_uniform.py` 各一条）

| 构建 | 泛光关 | 泛光开 | 增量 |
| --- | --- | --- | --- |
| 旧 1.7.2（4.5，合成器 CPU） | 2.83 s | 5.17 s | **+2.34 s** |
| 本版（4.5） | 2.17 s | 2.63 s | **+0.46 s** |
| 旧 1.7.2（5.2） | 2.11 s | 2.55 s | +0.44 s |
| 本版（5.2） | 2.12 s | 2.55 s | +0.43 s |

**总账（把 Emit 通道也算上，同一进程预热后交替取最小）**：

| 状态（4.5，3840×2160） | 旧 1.7.2 | 本版 |
| --- | --- | --- |
| 什么都没开 | 1.93 s | 2.14 s |
| 只开 Emit 通道 | 2.15 s（+0.22） | 2.45 s（+0.32） |
| **泛光全开** | **4.65 s（+2.72）** | **3.12 s（+0.99）** |

即开泛光的**总**开销 +2.72 s → **+0.99 s**；上面那张表量的是合成器那一段（+2.34 → +0.46）。
`_scratch/ab_three.py` 是三态脚本，`_scratch/ab_final.py` 是两态脚本。

三处改动：合成器切 GPU（4.5 默认 CPU）+ Glare `HIGH → MEDIUM` + 可选的
`GLOW_CANVAS`（默认 1.0 = 不降，只在 CPU 合成器上才值得开 0.5）。
设计与取舍都写在 `bv_glow.py` 顶部那段注释里；实测表格也在那儿。

### 还能不能再压？（结论：贴地板了，别再重复量）

4K 下剩下的约 +1.0 秒 = **Emit 通道 +0.33 + 合成器框架 +0.33 + 泛光运算 +0.33**（4.5 与 5.2 几乎一样）。
逐刀量过（`_scratch/bench_trim.py` / `bench_trim3.py` / `bench_trim4.py`）：

* 每多一个节点 ≈ **0.001~0.009 s** —— 删节点毫无意义；
* Glare MEDIUM→LOW 在 GPU 上 **0.00 s**；
* 删掉一层 Glare **−0.02 s** 但画面最大差 0.081（发平）；
* 去掉外发光模糊 / 整支外发光：**0.00 s**，胡桃那张图**逐像素一致**；
* "压到黑"节点画面一致但只省 0.03~0.09 s（噪声级，**故意没改**）。

要再省只能改效果（去掉 Emit 通道、或不起合成器），不是优化。所以别再花时间抠节点了。

**新增的坑（37-39）**

37. **`node.mute = True` 就是"删掉这个节点"的等价物，而且是交替 A/B 的好工具**：
    树结构不变、只切状态，跑起来的漂移自动抵消。同理，**预制两份组、切
    `group_node.node_tree`** 可以量"删掉一整支"的代价。4K 合成器的开销在进程之间能漂 0.5 秒，
    不交替量根本区分不出 0.02 秒级的差别。
38. **小心"改坏了反而更快"**：把某个 Mix 的输入拔掉不接，节点会用默认值（0.5 灰），
    画面直接过曝成白，而合成器可能把整条支路当死代码剪掉 —— 于是你量到一个"省 0.6 秒"的假象。
    凡是量出大数字，先看逐像素差（真省钱的那一刀，画面差必须小且**在你预期的地方**）。
39. **外发光的门槛 `自发光 > 0.60` 对深色模型根本不触发**（`增益` 插座没人设过，一直是 1.0）：
    胡桃这张图删掉整支外发光，画面逐像素一致。也就是说那条 5 节点 + 1 模糊的支路，
    只在奥黛塔那种"皮肤衣服都亮"的模型上才真的在干活。

### 这一轮新踩的坑（32-36）

32. **同一台机器上，泛光的开销几乎全在"合成器设备"上**：4.5 的
    `scene.render.compositor_device` **默认是 CPU**，同一个 4K 场景泛光增量
    CPU +3.01 s / GPU +1.04 s。5.2 默认已经是 GPU。切设备**不改画面**
    （逐像素最大差 0.004），但一定要**把用户原值记下来、摘泛光时还回去**。
33. **GPU 合成器上"降分辨率算"完全不省**：泛光的开销变成"每个节点一次调度"的固定成本，
    0.5 画布 +0.49 s vs 全画布 +0.47 s（4K）。所以 `GLOW_CANVAS` 默认 1.0 ——
    不要因为"降分辨率看起来更聪明"就默认打开，它只会让画面变一点点。
34. **跨进程的时间不可比**：同一状态在不同 Blender 进程里能差 0.4 秒（4K 基线
    2.15 ~ 2.51 s 都出现过）。而且**合成器第一次求值**（编译/分配）会额外吃掉
    1~1.5 秒 —— 冷启动单帧量出来的"泛光开销"能比稳态大一倍。
    可靠口径：**同一个进程内、先预热一帧、然后"关/开"交替量、取最小与中位**，
    见 `_scratch/ab_final.py`。
35. **`use_compositing=False` 时 Emit 通道不会被渲染**（消费它的合成器关着），
    所以"关掉合成器"就是干净的"没泛光"基线；反过来 `use_pass_emit=True` 单独开着也
    不代表要多花时间，别把它算进泛光开销里。
36. **审计脚本里的断言会过期**：腮红删掉后面板少一个按钮，`ops>=9` 就永远失败；
    而"没东西可摘"的 `remove_glow`、"模型里没有目影"的 `set_eye_shadow` 返回
    `CANCELLED` 本来就是对的。判断"是不是我这次改坏的"最省事的办法：
    **拿旧 zip 跑同一个审计**（`_scratch/audit_zip.py`），FAIL 集合一样就不是新问题。
