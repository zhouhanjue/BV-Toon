## 1.1.7 —— MMD 材质还原度大修

这一版把「看起来像 MMD 原生」这件事往前推了一大步，并且修掉了两个让画面发灰/发花的硬 bug。

### 修掉的两个硬 bug

* **泛光出现绿色重影** —— Blender 4.5/5.x 把 Glare 节点的选项从属性改成了**输入插座**，
  而且枚举变成首字母大写（`Bloom` 不是 `BLOOM`）。旧代码用属性赋值 + 静默 `try/except`，
  一个参数都没设上，节点一直跑默认的 `Streaks`/`Ghosts` —— 画面因此出现彩色重影。
  现在按插座名设置，并且**失败会打印**，不再静默吞掉。
* **宝石/闪片/金属全没了** —— 之前为了治"衣服油腻"，我把球面层强度一刀压到 0.30，
  但 MMD 的球面贴图有两种语义：**加算（mode 2）= 闪片、宝石、金属、目光**，
  这一层就是效果本体；**乘算（mode 1）= 布料上的柔和球面**，压它才是"去油腻"该做的。
  现在按模式分开：加算保持 **1.0**，乘算用预设值（**0.30**）。

### 新增

* **MMD 渐变贴图（toon ramp）驱动明暗** —— 按 MMD 的查表方式：**U = 0.5、V = 受光程度**，
  采样材质自带的 toon 贴图（含共享 `toon01–10`）当暗部遮罩；没有该贴图的材质自动退回自建条带。
* **可调描边粗细** —— 面板「描边粗细」+「应用」按钮，改完即时生效，不用重跑一键卡渲。
  默认 **0.08**（= mmd_tools 原值），想加粗直接填 0.2 / 0.4 / 0.8。
* **材质自带描边参数** —— 读 `edge_color` / `edge_weight`，逐材质给 `mmd_edge.<材质名>` 上色。
* **一键卡渲自动把色彩管理切到「标准」** —— AgX/Filmic 会把卡渲的饱和色洗淡、把明暗压平，
  这也是此前"发灰、发淡、偏平"抱怨的一大半原因。
* **环境色（ambient）接入暗部色调** —— 只有环境色**带颜色信息**（三通道不等）时才生效，
  避免被"统一的灰"污染预设的冷色暗部。
* **独立「Toon」标签页** —— 不再和别的插件挤在同一个侧栏标签下。

### 行为调整

* **一键卡渲 = 卡渲 + MMD 边缘预览**；「设置目影」拆成独立按钮（面板「其他设置」里）。
* **默认取消阴影**（`暗部深浅 = 0`、`分界暖边 = 0`）。想要明暗，把「暗部深浅」调上去即可。
* 卡渲节点组装在自带的 `BVToonData/BVToonShading.blend` 里（**可直接打开手改**），
  缺资产时自动回退到代码现场生成。

### 已知未做

* 材质名特殊规则（`发+` 加算高光、`目光/目影`、`肌` 透红、`スフィア`）—— 计划中
* 副纹理（高光贴图）接进高光通道 —— 计划中

### 工具链（`tools/`）

`build_assets.py`（生成资产）· `render_toon_ab.py`（同机位 A/B + 逐像素对比，透明背景只统计模型像素）·

## 1.6.0 —— 完整性校验（哈希防盗）

这一版让插件自己证明「有没有被人改过」：打包时把清单算好，**加载时**与**每次渲染前**各核对一遍，
对不上就自己带着标记 —— 但**绝不阻止渲染**。

### 清单（打包时生成）

* 打包时生成 `BVToonData/integrity.json`，内容是 **7 个顶层 `.py`**（`__init__.py` /
  `bv_integrity.py` / `bv_damage.py` / `bv_glow.py` / `bv_materials.py` / `bv_shading.py` / `bv_util.py`）
  **＋ `BVToonData/BVToonShading.blend`** 的 **SHA-256**，随 zip 一起发出去
  （zip 里一共 **11 个文件 + 1 份清单**）
* 核对时机：**加载时** + **每次渲染前**（带大小/mtime 缓存，代价只有几次 stat）
* 新增模块 `bv_integrity.py` —— **不导入 `bpy`**，所以打包/安装脚本能复用同一套规则
* 版本号现在**只在 `bl_info` 写一次**：面板底栏、条款弹窗标题都从它取（以前是硬编码，容易对不上）

### 水印三态

| 状态 | 触发条件 | 水印 |
|---|---|---|
| 正常 | 清单在且文件都对得上 | `渲染 BVToon / @BVan`（白字、字号 18、85% 透明、无底框） |
| 未授权修改版 | 清单在，但有文件被改 / 丢失 / 多出一个顶层 `.py` | `未授权修改版 / UNAUTHORIZED MODIFIED COPY`（红字、字号 24、**完全不透明** + 半透明黑底） |
| 未验证副本 | 没有清单，或清单读不懂/格式不对 | `未验证副本 / UNVERIFIED COPY`（同样红字不透明 + 黑底） |

* **为什么分三态**：从 GitHub 源码目录直接拷进 `addons` 的人（或自己改代码的人）不该被当成盗版 ——
  清单是**打包产物**，源码目录里本来就没有。所以「对不上」= 修改版，「没有清单」= 未验证；
  **两种都不会再印出 `渲染 BVToon / @BVan`**
* 异常状态时：**控制台打印一整块醒目警告**（含具体是哪些文件 + "自己改了代码想恢复正常水印
  就重跑安装/打包脚本重算清单"）+ **面板最上面多一块红色告警框**（`alert` 高亮）

### 行为与边界

* **绝不阻止渲染** —— GPL v3 允许修改与再分发，这里只做标记与警告
* **诚实前提**：哈希校验**不是加密**，懂行的人可以连清单一起重算；它挡的是"随手改个名就说是
  自己写的"那种改法，并让改过的副本自己带着标记
* **与许可的关系**：LICENSE 里 §7 附加条款第 2 条本来就要求「修改版必须以合理方式标明与原始
  版本不同」，这个水印就是那条要求的**技术实现**（不是新增限制）
* 面板「使用条款」弹窗新增**第 5 条**，说明这个哈希校验行为（中/英/日三语都有）

### 工具链（`tools/`）—— 打包脚本这次是真的

* **坑**：`tools\package_bv_toon.py` 与 `tools\install_bv_toon.py` 以前其实是 MBTs 时代的旧脚本
  （指向工作区根目录那个"不可上架的私有版"），**HANDOFF 里写的打包命令实测直接报错退出**
  （`REFUSING: missing BV_Toon_Fix.py`）—— 照着文档做反而装不出来。
  现在这两个名字下是真正的 **clean-room 打包/安装脚本**
* 旧脚本改名保留：`tools\package_private_mbts.py`、`tools\install_private_mbts_patch.py`
* 打包脚本会**拒绝**：版本与 tag 不一致、语法错误、缺文件、LICENSE 不是 GPL v3 + §7、
  插件里又出现硬编码版本号、`__init__.py` 没接 `bv_integrity.verify()`、仓库里缺三语
  `RELEASE-<版本>.md`；打完还会**把 zip 拆开核对**「清单里的哈希 == zip 里那些文件的哈希」
* `--verify` 会在**每个** Blender 里用一次性配置真装一遍，实测**五种情形**：正常 / 改一个字节 /
  多出一个 `.py` / 删掉清单 / 重算清单 —— 逐个检查水印文字与面板告警
* 体检脚本 `tools\audit_bv_toon.py` 也加了一整段完整性检查（清单覆盖范围、三态、水印文字与
  透明度、面板告警）

### 校验不过时：可以把画面弄坏（`bv_damage.py`）

* 面板「其他设置」新增 **`校验不过`** 三档：`只标记水印` / **`被改就损毁画面`（默认）** /
  `被改或未验证都损毁`
* 损毁 = **像素化（马赛克）+ 压色阶 + 去饱和压暗**，出图一眼就是废图；水印同时还是那行红字警告
* 走**合成器**（合成器是渲染管线的一部分）：静帧、动画、视口渲染都生效，不用去猜输出文件名改文件
* 恢复正常（重算清单）后节点会被**摘掉、接线还原**，不在别人的合成器里留常驻节点
* 节点名/插座名是**探测过的**（这项目的老坑：Glare 的参数就搬过家）：
  `CompositorNodePixelate` 是 `Color`/`Size`，`Posterize` 是 `Image`/`Steps`，
  `HueSat` 是 `Image`/`Saturation`/`Value`；图像混合 4.5 用 `CompositorNodeMixRGB`、
  5.2 起只有 `ShaderNodeMix`（由 `bv_glow._mix` 兜住）
* 诚实边界：开关是场景属性，能关掉；愿意改代码的人本来就能把整个校验删掉。
  它拦的是"拿改过的副本出图冒充原版"—— 让那些图自己废掉。GPL v3 允许修改与再分发，
  这里动的只是**这个副本自己渲染出来的画面**

### 修：重新加载文件之后，强制署名会静默失效（渲图当场抓到的真 bug）

* **症状**：同一机位渲三张不同完整性状态的图，水印**一模一样** —— 全是正常署名
* **原因一**：`wm.read_homefile`（文件 > 新建）与 `wm.read_factory_settings` 会**清空
  `bpy.app.handlers`**；处理器没有 persistent 标记就没了，而"面板绘制时补挂"只在
  **有人打开 Toon 面板**时才发生 —— 后台渲染根本没有面板可画，于是静默失效
* **原因二**：工厂重置还会把插件一起关掉，而 Blender **重新启用**插件时不会再跑一遍
  模块顶层代码，所以只在文件末尾挂一次的话，重新启用之后再也挂不上
* **修法**：处理器加 `@bpy.app.handlers.persistent`；挂载收进 `mount_watermark_handler()`，
  由 `register()`（每次启用）与面板绘制各补一次；`unregister()` 顺手摘掉
* **回归测试**：`package_bv_toon.py --verify` 与 `audit_bv_toon.py` 现在都会真渲一张 64×64 ——
  先把水印破坏成「入侵者」，再看处理器有没有把它设回来（新建文件 / 工厂重置+重新启用 两条路径都测）
* 连带把 `force_watermark` 里"拿不到 scene 就静默 return"改成会打印原因
* 效果图与复现步骤：`_damage_demo/`（同机位四步渲染 + 水印放大裁图）

### 安装注意

* 从源码目录手工拷贝安装的副本**没有清单**，水印会显示「未验证副本」；用 Release 里的 zip，
  或在副本目录跑 `python tools\install_bv_toon.py --target <目录>` 就会补上清单

### 已知未做

* 材质名特殊规则（`发+` 加算高光、`目光/目影`、`肌` 透红、`スフィア`）—— 计划中
* 副纹理（高光贴图）接进高光通道 —— 计划中

## 1.7.0 —— 腮红重做（只给脸 + 用模型自带的腮红贴图当遮罩）

1.6.0 与 1.7.0 是同一次交付（1.6.0 未单独发布），完整性校验 / 水印三态 / 损毁画面那些都在
上一节里；这一节是 1.7.0 新增的部分。

### 腮红只加在脸上（`bv_materials.py`）

* 「添加腮红」以前是**无差别写到每个卡渲材质上** —— 实测这个模型 39 个材质全中，
  衣服、头发、裙子、腿一起泛红。现在先认出"脸"，只写它，**并把其余材质上的腮红清零**
* 认脸的办法（先准后宽，命中就停）：① 材质名里有 `颜/顔/脸/face/フェイス…`
  ② 用它的网格名里有 ③ 底色贴图名像脸且唯一 ④ 唯一的肤色材质（`肌/skin`）。
  **一种都没命中就报警并把材质名列出来**（绝不猜、也绝不"干脆全加"）
* 面板模式＝`替换单个【材质】`时听用户的：直接用当前激活的材质槽，不看名字
* 面板上多了一行 `脸材质：颜`，点完就知道刚才加到了谁身上
* **顺带修掉一个"假有效果"**：腮红遮罩是 `clamp((范围 - 亮度) / 过渡) × 浓淡`，默认范围 0.62
  而这张脸渲出来亮度中位数约 0.85（脸上多在 0.9~0.97）⇒ **阈值对脸完全够不着**，
  只加脸时实测 **0 个像素变化**；以前"看着有效果"是因为它糊在了衣服和皮肤上。
  在真实模型上量过之后，默认改成 **范围 0.99 / 过渡 0.20 / 浓淡 0.80** —— 脸颊、鼻梁、
  下巴、眼睑泛红，头发衣服手臂一点不变（`tools/check_blush_face.py` 用像素断言：
  头部区域外出现变化直接判失败；另有"全都加"的对照组，证明这套测法测得出跑偏）
* 回归测试：`tools/check_blush_face.py`（渲三张 + 逐像素断言）、`tools/audit_bv_toon.py`
  新增 8 项腮红检查

### 腮红：优先用模型自带的腮红贴图当遮罩（`照れ`）

* 先做**行为对照**（只跑那个私有旧版、不读它代码，见 HANDOFF 第 19 条）：
  它的腮红也是只动脸部（1090 像素、行 922–952、只压 G/B 通道 ⇒ 加红），
  比我们当时的纯着色器版**更窄更浓**（我们是 2498 像素、行 900–981）
* 于是按第一原理改：**优先拿模型自带的腮红贴图（`照れ` 之类）当遮罩** —— 形状是作者画的
  * 这种贴图是**用 alpha 画图案**的：实测 `照れ.png` 是 2048²、**98% 全透明**、
    RGB 几乎是均匀浅粉（亮度均值 0.858）⇒ **拿亮度当遮罩完全没用**，必须走 alpha
  * 卡渲组新增输入 **`腮红贴图`**（默认 1.0 = 不接贴图，行为与以前完全一样）；
    插件在脸部材质树里插 `bv_blush_tex`（贴图，UV 跟底色贴图一致）+
    `bv_blush_mask`（`Map Range`：alpha 0.15 以下当没有、0.50 以上当满遮罩）——
    照れ 的 alpha 整体很淡，直接乘会把腮红抹没（实测只剩 38 像素）
  * 渲染结果：**两个明确的脸颊红点**（192 像素、跨 8 行），而不是整脸一片潮红（2096 像素、跨 63 行）
  * 模型没有这种贴图 → 自动退回原来的着色器腮红（亮度阈值那套）
* 面板会显示用的哪条路：`腮红：用模型自带的腮红贴图「照れ.png」当遮罩`
* 试过但**否掉**的路：把模型那个 `颜+`（照れ）材质"放出来"（alpha 置 1）——
  MMD 的照れ 材质是"漫反射白 + alpha 0"的 morph 材质，只放 alpha 会渲成**黑脸**（实测），
  要修就得改 `mmd_material` 数据，跟我们"不改写 MMD 数据"的承诺冲突
* 顺带修掉一个自己写出来的 bug：遮罩接线时把组输入变量覆盖掉了，遮罩接到了 `Map Range`
  自己的插槽上（组的输入根本没接）—— 被 `check_blush_face.py` 的断言当场抓住

### 损毁没有档位可选（永远最严格）

* **这个设置项整个删掉了**：早先版本做过"三档下拉框"（`只标记水印` / `被改就损毁画面` /
  `被改或未验证都损毁`），后来又改成"校验不过时强制第三档并上锁" ——
  按作者要求，最后**连设置项都不留**：场景属性、面板下拉框、模块里的档位常量全部删除，
  也没有"只标记水印"这种温和档可走
* **规则只剩一条**：校验通过 → 画面照常；校验不过（被改 / 未验证）→ 画面一定被损毁
  （像素化 + 压色阶 + 去饱和压暗）
* 面板上只留一行说明（不是选项、点不动）：`损毁：被改或未验证都损毁（唯一档位，无选项）`；
  校验不过时顶部另加红色告警块
* **代价（知情后选的）**：因为"未验证"也算不过，所以从源码目录直接拷进 `addons` 的副本
  （没有清单）**也会被损毁**；恢复正常只有一条正路：跑一次 `tools/install_bv_toon.py` 重算清单
* 效果图与断言：`_damage_demo/`（四步：正常 → 被改损毁 → 未验证损毁 → 恢复）；
  `package_bv_toon.py --verify` 与 `audit_bv_toon.py` 都断言
  **场景上没有损毁档位属性**（`not hasattr(scene, "bv_damage_mode")`）、
  **面板任何状态下都不画这个属性行**、以及损毁强度表（被改/未验证 → 1，通过 → 0）
* 这一节的过程留档：先是"三档 + 面板可改" → 改成"校验不过时强制第三档并上锁（属性还在、
  恢复后还回用户档位）" → 最终"整项删除"；每一步都是被真实反馈推进的，
  断言也跟着从"面板有没有禁用某行"变成"属性是否存在"

## 1.7.1 —— 腮红重做第二版（这次是真的看得见了）

1.7.0 的腮红在**很多模型上根本看不见**（老 PMD 的 初音ミク / MEIKO / 鏡音リン / 巡音ルカ，
以及一批游戏角色）。这一版把它掀开重做：**遮罩不再看明暗，只看几何**。

### 三个原因（都量过，缺一个都解释不了现象）

* **绝对亮度阈值**：旧遮罩是 `clamp((腮红范围 1.10 − 亮度) / 腮红过渡 0.30)`。老 PMD 的脸是
  **纯白贴图 × 亮度 1.05**，渲出来常年 >1 ⇒ 这一项恒 0 ⇒ 初音ミク / MEIKO / 鏡音リン 实测
  **0 像素变化**（`_scratch/probe_pmd_truth.py`、`probe_blush_extreme.py`）
* **换成"相对亮度"（除以自己的峰值）照样恒 0**：探针 `probe_relative.py` 把组内部的值当颜色
  通道渲出来量，**最终色是参考峰值的 1.0~4.6 倍**，阈值依旧够不着
* **脸颊球心的算法让球只是"擦"过脸**：原先是"脸中心 + 沿脸朝向推 55% 凸出"，球心落在头颅
  里面，球面和颊面几乎不相交

**把它揪出来的实验**（`_scratch/probe_giant_cheek.py`）：把脸颊半径设成 100（遮罩恒 1）——
胡桃立刻 **2300 像素**变化，默认半径只有 **21 像素** ⇒ 问题在遮罩，不在"腮红有没有接进最终颜色"。
**先隔离"有没有生效"和"值算得对不对"，别一口气猜三个原因。**

### 现在怎么算

* 遮罩 **`= 腮红保底 + (1 − 腮红保底) × 脸颊圈`**，纯几何，没有任何能整体归零的项。
  `腮红保底` 默认 **0.35** → 整块脸材质都有一点气色，两颊最浓
* **脸颊圈贴着几何算**：取脸材质自己的顶点 → 只留颈部以上 → 在"脸的左右/上下"平面里挑
  **离目标点最近的真实顶点**当球心（保证球切得到颊面）→ 再沿脸朝里压进半径的 55%
  （让球与颊面交出一个圆盘）。半径 = 脸半宽 × 42%，软边 55%，比例全按
  **物体局部坐标**算（和 `TexCoord.Object` 同一套）⇒ 模型多大、导入比例多少都不用改数字
* 组输入：**新增** `腮红保底 / 腮红左 / 腮红右 / 腮红半径 / 腮红软边`；
  **删除** `腮红范围 / 腮红过渡`（就是那两个坑）
* **腮红色压深**：`(1.0, 0.62, 0.66)` → `(1.0, 0.52, 0.56)`。旧色跟肤色只差 ~0.2，
  实测最大像素差只有 **0.05** —— 数字上"有变化"，人眼一片没有
* **认脸猜得太小时会说出来**：猜到的脸材质 **面数 < 128**（实测 鏡音リン：颈部以上只有一块
  58 面的材质，那是眼睛/嘴之类）→ 面板弹红字 + 报告里带 ⚠，让人选中真脸材质按「脸=当前材质」。
  **宁可说"我认不出来"，也不默默加到错的地方**
* 模型自带 `照れ` 贴图那条路（alpha 当遮罩）沿用 1.7.0 的做法，未改

### 验收（9 个模型，640×853，EEVEE，同机位，断言"变化只在头部"）

| 模型 | 变化像素 | 模型 | 变化像素 |
|---|---|---|---|
| MEIKO | 5547 | 胡桃 | 1203 |
| 初音ミク | 661 | 芙宁娜 | 549 |
| 巡音ルカ | 1775 | 雷电将军 | 444 |
| 沃雅妮莎 | 633 | 蕾米埃尔-白 | 200 |

鏡音リン 仍然是 0：那个模型没有可识别的"脸"材质，面板会红字提示手动指定。
（这轮之前的旧实现：PMD 三个模型 0 像素，脸颊圈版也只有 21~75 像素。）

### 工具坑（害得一轮数据全废，值得单独记）

* **Blender 渲图不认相对路径，而且是"静默不写"**：`scene.render.filepath = "out/x.png"` +
  `write_still=True` 一个文件都不写也不报错；紧接着 `bpy.data.images.load("out/x.png")`
  **竟然不抛异常**，返回一张莫名其妙的图 ⇒ 后面的像素统计全是垃圾。
  现在所有验收/探针脚本一律 `os.path.abspath()` 输出目录
* 复现/看图工具：`_scratch/check_blush_corpus.py`（跨模型断言）、`probe_mask_only.py`、
  `probe_giant_cheek.py`、`probe_blush_apply.py`、`probe_face_pick.py`、
  `crop_head.py` / `crop_rect.py` / `diff_amp.py`

### 升级注意

* 组定义变了（现在 **75 节点 / 31 接口**），升级后请**再点一次「一键卡渲」**（或「添加腮红」），
  旧材质上的 `腮红范围 / 腮红过渡` 不再被读取

## 1.7.2 —— 泛光不再"看人下菜"（深色角色和奥黛塔一样亮）

作者反馈：**泛光不统一，胡桃等角色明显低于奥黛塔**，要求把所有角色都提到奥黛塔那个量级。
量下来是真的：同一套参数、同机位（640×853 EEVEE），**奥黛塔剪影外那圈光 +0.160，胡桃只有 +0.017**。

### 原因：整条泛光链吃的都是**绝对亮度**

* 泛光的源是渲染的 Emit 通道（卡渲本来就是全自发光）+ 画面里超过 `阈值 0.95` 的部分；
  外发光还有一道"自发光三通道最大值 > `0.60`"的门槛
* 于是"角色本身多亮"直接决定"泛光多亮"：

| 模型 | 角色平均亮度（关泛光） | 角色上的泛光增量 | 剪影外那圈光 |
|---|---|---|---|
| 奥黛塔（皮肤衣服都白） | 0.735 | +0.0497 | **+0.160** |
| 芙宁娜 | 0.586 | +0.0075 | +0.029 |
| 胡桃（深色衣服） | 0.421 | +0.0060 | **+0.017** |
| 初音ミク | 0.964 | +0.0099 | +0.271 |

* **试过但否掉**：按"材质平均底色 × 亮度"折一个增益。**不准** —— 材质的平均亮度预测不了
  "屏幕上亮部占多大比例"：胡桃按材质算只要 1.44 倍，实测要 ~9 倍才追平

### 现在：加了相机就**实测**，不猜

* 点「添加泛光」时渲两张 **192×192**（强度 0 / 当前值），量**剪影外那圈光**被提亮多少
  （"关着是黑、开着才亮、且贴着剪影 2 像素以内"的像素求平均），然后**闭环**：
  不够亮就按比例加，最多重来 3 轮（"关"的那张只渲一次）
* 目标值 **0.16** —— 就是奥黛塔在大家认可的那套设置下量到的值
* **只往上调，不往下压**：本来就比 0.16 亮的角色（初音ミク 0.271）一动不动，
  作者要的是"别让深色角色比别人暗"，不是"把亮的也压下去"。自动值夹在 `[0.03, 2.50]`
* 量不出来时（没相机 / 没框住 / 剪影外少于 12 个像素）**如实说**（报告 + 场景属性 `bv_glow_note`），
  强度保持默认 0.10，不假装量过
* 测量期间临时把分辨率压到 192、关掉署名，并**临时摘掉强制署名处理器**（白字会污染测量），
  量完立刻挂回去（`audit_bv_toon.py` 现在专门断言这一点）；渲染设置全部还原、临时图删掉
* 新增组输入 **`增益`**（默认 1.0）：手动乘在"自发光"那一支上，位置在**外发光门槛之前**，
  所以门槛也跟着变成相对这个模型的（深色角色终于也有剪影外那圈光）
* ⚠️ 量的时候那一圈必须按**画面比例**取（192 取 2 px ≈ 1%）：泛光半径本身就是画面百分比，
  取宽了就把紧贴剪影的亮芯算进来、量出的响应偏大（96 px 取 3 px 时胡桃被量成 0.265，
  全分辨率其实只有 0.166）。一次测量也不够准（泛光在亮部会顶到 1.0：奥黛塔每单位响应
  在强度 0.10 时是 1.49、1.2 时只剩 0.43）—— 所以闭环迭代

### 效果（同机位、各自自动强度下）

* 剪影外那圈光：奥黛塔 **0.152**、胡桃 **0.144**、芙宁娜 **0.142** —— 相差 **1.07 倍**（原来 7 倍）

## 1.7.2 修订 —— 腮红按几何重做（作者反馈"还是不够完美"）

版本号按作者要求仍是 **1.7.2**（他不接受更高的版本号），改动只动腮红这一块。

### 原来的两个毛病（都在真模型上量出来）

* **腮红压在眼睛上**：老写法把颊心放在"脸心往下 5% 半高"，而脸材质包围盒的中心
  **差不多就在眼睛高度**（上沿是额头/帽檐）—— 实测胡桃的腮红 **33% 的变化量落在"眼睛带"、
  鼻颊带只有 9%**，看着像"眼睛肿了"而不是"脸颊红"。
* **整脸连额头一起染红**：遮罩是 `保底 0.35 + (1-保底) × 脸颊圈`，那个 0.35 是**整张脸**的，
  额头、眼皮一起上色（初音ミク 8%、奥黛塔 12.8% 的变化量在额头顶那一带）。

### 现在的做法

* **按几何找颧骨**（不再用拍出来的比例）：眼线 = 同一网格上眼睛类材质顶点的平均高度；
  下巴 = 脸顶点最低处；**颊面 = 眼线往下 42% 的"眼线→下巴"跨度**；
  左右 = 在颊面那一带里取横向最外的顶点，**另一侧跨脸中线镜像**（人脸本来就对称，
  两侧独立取点会一大一小）。
* **上界软切**（卡渲组新增三个输入 `腮红上界法线 / 腮红上界 / 腮红上界软边`）：
  物体坐标投影到"脸自己的上"方向，过了上界就淡出 —— 只切**内置遮罩**，
  模型自带腮红贴图（照れ）是作者画的形状，不切。
* 保底 0.35 → **0.18**、颜色 (1.0,0.52,0.56) → **(1.0,0.44,0.50)**（浅肤色模型上才看得见）、
  球心压入 0.55 → **0.45**（必须比"满遮罩区"浅，否则颊面上没有任何一点能到 1）、
  半径 = 中线→颧骨 × **1.05**。

### 实测（`_scratch\dbg_blush_face.py`，脸特写 320×320，含"摘掉贴图遮罩"的纯着色器路径）

| 初音ミク（老 PMD，脸被刘海挡） | 272 | 0.192 | 233 / 39（一侧被头发挡住） |

验收：`check_blush_face.py` **failures=0**（5 个模型）；`audit_bv_toon.py` **2 个已知假失败**
（`remove_glow` / `set_eye_shadow` 返回 CANCELLED 属正常）。

### 顺带修掉的脚本问题

  后者在小脸模型上显式跳过并报数。

## 1.7.2 修订（三）—— 泛光性能（开泛光的代价从 +2.9 秒降到 +0.5 秒）

作者要求：「性能优化，不启用泛光要3秒，启用却要7秒（尽可能的优化性能到最少）」。

结论先放这儿（**3840×2160、胡桃、同机、预热一帧后"关/开"交替各 3 轮取中位**）：

| 构建 | 泛光关 | 泛光开 | 开泛光多花 |
| --- | --- | --- | --- |
| 旧 1.7.2（4.5，合成器默认 CPU） | 2.83 s | 5.17 s | **+2.34 s（+97%）** |
| 本版（4.5） | 2.17 s | 2.63 s | **+0.46 s（+21%）** |
| 旧 1.7.2（5.2） | 2.11 s | 2.55 s | +0.44 s |
| 本版（5.2） | 2.12 s | 2.55 s | +0.43 s |

再把三种状态分开量（同一进程、预热一帧后交替、取最小）：

| 状态（4.5，3840×2160） | 旧 1.7.2 | 本版 |
| --- | --- | --- |
| 什么都没开 | 1.93 s | 2.14 s |
| 只开 Emit 通道 | 2.15 s（+0.22） | 2.45 s（+0.32） |
| **泛光全开** | **4.65 s（+2.72）** | **3.12 s（+0.99）** |

也就是：**开泛光的"总"开销（Emit 通道 + 合成器）从 +2.72 秒降到 +0.99 秒（约 1/2.7）**，
其中合成器那一段从 +2.34 秒降到 +0.46 秒（约 1/5）。剩下的 +0.99 秒里，
Emit 通道（+0.3 秒）是泛光的光源、省不掉，其余是合成器每个节点的一次调度。
作者那边的 3 秒 / 7 秒，按同一比例大致会变成 3 秒 / 4.5 秒。

### 改了三处（按收益排序）

* **合成器切 GPU** —— 4.5 的合成器**默认走 CPU**，而泛光整条链都在合成器里。
  4K 实测：CPU 上泛光增量 **+3.01 秒**，GPU 只要 **+1.04 秒**，而且两张图**逐像素一致**
  （最大亮度差 0.004）。点「添加泛光」时自动切到 GPU；**用户原来的设置会被记住，
  摘掉泛光时原样还回去**。5.2 默认已经是 GPU，不动它。
* **Glare 质量 HIGH → MEDIUM** —— 两层 Glare 是泛光里最贵的一段。4.5 的 CPU 合成器上
  HIGH→MEDIUM 省 **0.6 秒**、HIGH→LOW 省 0.8 秒，而画面最大亮度差只有 **0.016**（MEDIUM）
  / 0.028（LOW）：泛光是大半径低频的东西，金字塔少一级看不出来。
* **可选的降分辨率计算（`GLOW_CANVAS`，默认关）** —— 把泛光前段放到 1/N 画布上算、
  末尾再升回全分辨率（画面本身不经过降采样）。量下来**只有 CPU 合成器上划算**：
  0.5 画布让 4.5 CPU 的增量从 +3.38 秒掉到 +1.13 秒；但 GPU 合成器上一点都不省
  （+0.47 vs +0.49），却会让剪影外的光往外摊一点（角色上的泛光 **-16%**）。
  所以**默认 1.0：一个像素都不动**，只在"显卡用不了、只能 CPU 合成"时手改成 0.5。

### 画面到底变了多少（4K 同机位逐像素）

* 4.5：全画面平均差 **0.0021**、最大差 0.0196；**剪影外那圈光 0.0669 → 0.0668（没变）**。
* 5.2：平均差 0.0015、最大差 0.0118；剪影外 0.0561 → 0.0581。
* 跨模型统一性（`tools/check_glow_uniform.py`，奥黛塔/芙宁娜/胡桃/雷电将军）
  **failures=0**，最大/最小 **1.14 倍**（旧版 1.09 倍）。
* 唯一能测出来的差别：**角色身上**沾到的泛光比旧版低约 **9%**（0.0841 → 0.0766，
  暗色模型上更明显）。原因是 Glare 降到 MEDIUM 后外层金字塔少一级，光更集中在外圈；
  剪影外那圈（"泛光看得见的那件事"）没动。想要旧版的贴合感，把 `bv_glow.GLOW_QUALITY`
  改回 `"HIGH"` 即可。

### 还能不能再压？（量完了：不能，已经贴地板）

作者追问"还可以压缩到极致吗"。把 4K 下剩下的约 +1.0 秒逐段量开（同一进程、
预热后交替取中位，脚本 `_scratch/bench_trim.py` / `bench_trim3.py` / `bench_trim4.py`）：

| 这一段 | 4.5 实测 | 5.2 实测 | 能不能省 |
| --- | --- | --- | --- |
| Emit 通道（多渲一张 AOV，泛光的光源） | +0.33 s | +0.34 s | **不能** —— 去掉它泛光就不再由"模型自己的自发光"驱动 |
| 合成器框架（空树 RLayers→Composite 也要花） | +0.33 s | +0.35 s | **不能** —— 只要用合成器就要付 |
| 泛光本身的运算（两层 Glare + 模糊 + 15 个逐像素节点） | +0.33 s | +0.33 s | 见下 |

逐项验证"泛光本身"这 0.33 秒能不能抠（都是交替 A/B，两条曲线漂移自动抵消）：

* **每多一个节点 ≈ +0.001 ~ 0.009 s**（往树里插 4 个"原样穿过"的节点量出来的）
  —— 所以删节点是白费劲：删 4 个才 0.03 秒。
* **Glare 质量 MEDIUM→LOW**：GPU 上 **0.00 s**（只在 CPU 合成器上省 0.18 s）。
* **只留一层 Glare**（删掉贴着亮部的 core）：**−0.02 s**，而画面最大差 0.081（看得出来发平）
  —— 白赔画面。
* **去掉外发光模糊**、**整支外发光全删**：**0.00 s**，而且胡桃这张图**逐像素完全一致**
  （原因见下面那条：门槛 0.60 对深色模型根本不触发）。
* **"压到黑"节点**（LIGHTEN 夹负数）：画面逐像素一致，省 0.03 ~ 0.09 s —— 在噪声里，不值当改管线。

**结论**：剩下的 ~1 秒里约 2/3 是"多渲一张 AOV + 合成器本身要开着"，1/3 才是泛光运算，
而泛光运算里每一刀都只有 0.00~0.02 秒。真要再往下砍只剩两条路，都是改效果而不是优化：
把 Emit 通道去掉（泛光改成吃画面亮度）、或者干脆不起合成器。所以这一轮**没有改动管线** ——
量出来不值得为噪声级收益冒改画面的风险。真要省，只有 CPU 合成器的场合值得把
`GLOW_CANVAS` 改成 0.5（那一刀 2.25 秒）。

### 顺带修掉的工具误报

`tools/audit_bv_toon.py` 有三条**过时断言**（旧包同样失败，属误报）：

* 面板按钮数还按"有腮红"时的 **9** 个算 —— 腮红已按要求删除，现在是 **8** 个；

  返回 `CANCELLED` 被判成失败 —— 这两种 CANCELLED 都是正确行为。

现在只对**首次**调用要求 `FINISHED`；改完两个 Blender 的真实配置里审计 **0 FAIL**。
